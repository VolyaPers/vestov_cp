# Vestov HUB — функциональный аудит и план исправлений

> Исторический аудит до исправлений. Текущее состояние и проверки: [результат реализации](results.md).

Дата: 6 сентября 2026. Объект: локальный текущий checkout Vestov HUB. Запрос: проверить работоспособность существующего интерфейса с приоритетом зарплат, сотрудника, смен/отсутствий и клиента, подготовить план всех найденных исправлений.

## Результат

**Сейчас нельзя считать, что всё видимое в интерфейсе корректно работает.** Есть настоящие API, таблицы и рабочие базовые операции. Однако зарплатный раздел пока представляет журнал выплат с ненадёжным расчётом долга, три кабинета получают несогласованную календарную картину, а ограничения доступа обходятся прямыми запросами. Это влияет на деньги, состав команды, отпускные остатки и достоверность информации для клиента.

На отдельной копии базы воспроизведены отрицательная зарплатная запись, двойная запись одинакового платежа, создание администратора без входа, смена пароля существующего синтетического администратора без подтверждения, доступ клиента к общим данным сотрудников, публичная выдача файла и 500 в feedback. Чистые проверки настоящих вычислений дополнительно показали ошибки ставок, инвойсов, отпусков и отчётов.

**Границы проверки:** просмотрен код UI→API→БД и достижимые маршруты трёх кабинетов; браузером проверены загрузка страницы входа и переход к Clerk. Полный ручной прогон всех авторизованных экранов через Clerk, production и внешние платёжные/почтовые/Slack/ClickUp интеграции не выполнены. Подключённый обработчик не обозначается как успешно проверенный пользовательский сценарий. Это план исправлений по обнаруженным проблемам, а не гарантия отсутствия других дефектов.

Исходная база `vestov_portal` и прикладной код не изменялись. Записи выполнялись только в копии `vestov_audit_20260906`, преимущественно на новых синтетических сущностях; один разрешённый тест прав затронул скопированную запись сотрудника. Уведомления и интеграции в копии отключены. «Record salary» создавал учётные записи; реальных переводов денег не было. Добавлены только документы аудита и диагностические артефакты; публикации/деплоя не было. После проверок запущенные для аудита процессы остановлены, временная копия базы и тестовые session cookies удалены; секреты в диагностическом журнале скрыты.

## Правила, которые нужно утвердить до реализации расчёта зарплат

Ответ на вопрос о схеме зарплат во время аудита не получен. Поэтому нижеперечисленное — входные решения для реализации, а не придуманные финансовые правила.

1. Тип оплаты на сотрудника: месячная ставка, почасовая или индивидуальный вариант; дата начала/окончания действия условий, неполный месяц и изменение ставки внутри месяца.
2. Источник оплачиваемого времени: смены, подтверждённые ClickUp entries или утверждённый ручной табель. В системе есть все три набора данных; одно время не должно оплачиваться дважды.
3. Оплата vacation/sick/unpaid/half-day, перерывов, сверхурочных, выходных и праздников; единицы квоты — календарные дни, рабочие дни или часы по индивидуальному графику.
4. Авансы, extras, reimbursement, переплаты и перенос остатка; кто утверждает период и кто может корректировать закрытый период.
5. Только USD или несколько валют. Курс, налоги и удержания не определять по предположению.
6. Для клиента: какие исторические участники доступны при просмотре прошлого месяца; кто видит общие отзывы компании; достаточно ли публичного типа отсутствия без внутренних причин.
7. Требуется ли новый раздел расчётных листков сотрудника. Сейчас есть salary email, отдельного employee payroll кабинета нет: это функциональное дополнение, не сломанная существующая кнопка.

## Приёмочная матрица: что означает «всё в интерфейсе работает»

Общий критерий для каждой операции: корректное начальное состояние → действие → ожидаемый API/статус → правильная запись в БД → повторное чтение/reload → отражение во всех затронутых кабинетах. Отдельно проверить ошибки и недоступность операции для другой роли. Сначала финансовые/API инварианты, затем браузерный end-to-end.

| Область | Обязательный сценарий |
|---|---|
| Users / onboarding | Admin создаёт client/employee, назначает доступ → фактический Clerk-вход → нужный кабинет; неактивный пользователь не входит; правка email не теряет связь с человеком |
| Clients / Services / Team | Создать клиента A/B, два проекта одного типа, назначить трёх сотрудников, одного в оба проекта; изменить период/цену/роль, деактивировать назначение → нужная команда и история. Неверное сочетание client/service/member ID отвергнуто |
| Payroll monthly | Старый месяц по1000, новый по2000; частичная выплата400, доплата с `+` в названии, остаток600; future rate не меняет текущий период; закрытый месяц не переписывается |
| Payroll time-based | Отработано8ч, перерыв1ч, half-day sick/vacation, неоплачиваемое отсутствие, overtime, неполный месяц; ожидаемая сумма заранее рассчитана по утверждённой политике; ClickUp+shift одного интервала не суммируются дважды |
| Payments | Повтор запроса, две вкладки, отрицательная сумма, невалидная дата, ошибка email после сохранения → один корректный платёж/остаток и понятная ошибка. Исправление платежа через корректировку с аудитом |
| Leave lifecycle | Employee create → admin approve/deny → все календари/балансы; create-and-approve/edit/bulk дают те же правила. Future cycle, midpoint, year boundary, first year, exhausted quota, overlap sick/vacation, half-day, cancel past leave |
| Shifts | Preferred save → start → break → resume → end → history; новый preferred после использованного schedule; двойной start/break; override day-off/shift; notes; night/weekend и смена timezone |
| Client calendar | Назначение10–20 сентября видно в этом диапазоне; календарь другого месяца использует тот состав; последний день отсутствия, DST Europe/Kyiv↔America/New_York, half-day и общий сотрудник двух проектов |
| Feedback | General/team/employee → save → reload → admin response → client reload; A→B project switch, медленный предыдущий response, empty/invalid input, чужой recipient |
| Documents | Folder/upload/visibility/preview/download/rename/move/delete с сохранением после reload; новый файл после restart; read vs write; чужой documentId/raw URL запрещён |
| Invoices | Manual/service mode, выбранные участники, hourly/fixed/zero, create/edit/reopen, subtotal/total, pending/overdue/paid и paidAt; sum(rows)=stored amount=preview=list |
| Reimbursements | Два конкурирующих запроса на остаток лимита; approve/reject; receipt отдельно от paid; смена career year и фильтра; фактическая оплата попадает в финансы один раз |
| Reports / finances | 0/1/2+ decimal invoices, income/expense/salary/extra_payment, один клиент/все, month/quarter/year/custom, previous period, active/inactive/billable, статусы и recurring |
| Time Tracking / интеграции | Mapping сотрудника, sync/import, границы дат, retry/deduplication, service allocation и reconciliation с выбранным зарплатным источником часов; доставка уведомлений проверяется отдельно |
| Навигация / ошибки / mobile | Все реальные Layout routes, global search, tabs, filters, dialogs, cancel/save/reload, impersonation/return, logout; 401/403/500/offline/slow response; viewport390 и desktop1440 без потери управления |
| Прямой доступ | Аноним, employee, client A-read/A-write/B, admin: list/detail/mutation/totals/file/room. Ошибочный запрос не должен менять БД или раскрывать чужие данные |

Условие завершения: исправлены P0/P1; P2 из существующего видимого интерфейса также закрыты или заменены согласованным честным поведением; бизнес-правила утверждены; деньги сверены; миграции проверены на fresh/upgrade; матрица пройдена без условных skip вместо операций. Production готовность подтверждается отдельной проверкой реально развёрнутой версии.
