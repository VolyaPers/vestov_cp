## F01 — P0: открытая регистрация администратора и захват существующего аккаунта

`server/src/routes/auth.ts:77,274-558`: `ALLOWED_ROLES` включает admin, `/register` доступен без входа. Для существующего email сервер заменяет password произвольным новым без подтверждения владения email, старого пароля или одноразового приглашения, сохраняет существующую роль и выполняет `req.logIn`. Новый пользователь может передать admin. Ветка с googleId также доверяет полю запроса, не подтверждённому Google токену. Router подключён публично в `server/src/index.ts:329`. При этом `src/pages/AuthPage.tsx:92` обещает, что password registration удалена, а frontend требует Clerk.

HTTP-проверка на временных аккаунтах: анонимный register(admin) → 201 и сессия admin; `/users` с этой сессией → 200. Повторная анонимная регистрация существующего синтетического admin с новым паролем и role=client → 201, возвращённая роль остаётся admin. Исходные аккаунты не перезаписывались. Доказательства: `api-repro.json`, `api-finance-auth-repro.json`.

Фикс: убрать legacy register/login/claim из рабочего публичного API при переходе на Clerk; явно определить поддерживаемые способы входа. Роль назначает только уполномоченный администратор. Создание внутреннего профиля, приглашение и подтверждение внешней identity — разные операции с однозначной связью. Если legacy flow нужен, одноразовый ограниченный invite и проверка владения обязательны; role из запроса не доверять. После исправления проверить текущие доступы/сессии по журналу; необходимость их отзыва решать по фактам, без утверждения о произошедшей атаке.

Приёмка: аноним не может создать администратора, сменить пароль/identity существующего пользователя или получить privileged session; легальный Clerk-вход и admin-created users работают. Все три роли и отозванный доступ проверяются через UI и прямой API.

## F02 — P0: приватность документов обходится ссылкой или чужим document ID

`server/src/index.ts:348-350`: `/uploads` и `/api/uploads` раздаются express.static без requireAuth. `documents.ts:218-238,291-311`: preview/download для не-admin проверяют только visibleToClient, без членства в компании этого документа. `client.ts:125-138`: legacy list не фильтрует visibleToClient. `documents.ts:96-98`: любой team_member может upload в любую компанию.

HTTP: специально созданный безличный текстовый файл в uploads был прочитан анонимно через `/api/uploads/...` с 200, после проверки собственный файл удалён. Чужие реальные файлы не скачивались. Остальные обходы подтверждены кодом.

Фикс: публичным оставить только предназначенные для публикации изображения; документы и evidence хранить приватно, выдавать через проверенный file/document ACL. Проверять компанию, проект, тип объекта, active membership и write permission на каждом list/preview/download/upload. Исправить legacy routes; не считать непредсказуемый URL авторизацией. Проверить сохранность файлов при рестарте/деплое: текущий локальный disk storage и Render free service в конфигурации не являются доказательством постоянного хранения production.

Приёмка: аноним и клиент B не получают файл A ни по одному URL; клиент A видит разрешённый файл, hidden доступен только внутренней разрешённой роли; upload→reload→download совпадает по байтам; рестарт сохраняет файл. Отдельно проверить папки, перемещение, скрытие, переименование и допустимые MIME/размеры.

## F03 — P1: live-события смен не изолированы по ролям и клиентам

`server/src/socket.ts:48-60`: соединение и join:admin/join:client не проверяют session/role/membership. `:81-104`: события отправляются только в room admin, включая employeeEmail, breakNote и сведения проекта. `src/hooks/useSocket.ts:99-109` клиентский слушатель также вступает в admin room. CORS не заменяет авторизацию WebSocket.

Фикс: аутентификация handshake, server-derived комнаты по роли/назначениям, минимальный client event DTO, рассылка в фактическую компанию. Исключить причины отсутствий и внутренние notes. `useSocket.ts:47` использует fallback localhost:3001, поэтому отдельно в deploy config закрепить корректный WSS endpoint и проверить reconnect; наличие env в production в этом аудите не проверено.

Приёмка: аноним не подключается к приватным событиям; клиент A не вступает в admin/B room; start/break/end своей команды обновляют UI A и admin; reconnect сохраняет правильную подписку. HTTP polling и WebSocket дают одинаковый статус.

## F04 — P1: журнал запросов пишет пароли, cookies и финансовые тела

`server/src/index.ts:267-280` логирует все headers и body, кроме Slack project bot; `auth.ts:563` повторно логирует пароль login. В локальном runtime журнал действительно содержал тестовые session cookies и password. Это текущая работа кода, а не предположение.

Фикс: структурированный allowlist журнала: request ID, route, status, latency; redact authorization/cookie/password/token и чувствительные поля до записи. Финансовый audit сохранять отдельно с минимальными необходимыми полями и доступом. Не публиковать сырые журналы.

Приёмка: тестовый уникальный secret не встречается в логах при успешном и ошибочном запросе; финансовая операция сохраняет автора/время/изменение без секретов.

## F05 — P1: запуск сервера может удалять сотрудников без email

`server/src/index.ts:431-464,539-542`: startup fix при первом запуске ищет несвязанных с users сотрудников и удаляет запись, если email пустой. Если есть ссылки, может упасть FK; если нет — исчезает карточка. Состояние выполнения хранится в script_execution_log. На проверенной копии скрипт был ранее помечен выполненным, поэтому при этом запуске удаление не выполнялось.

Фикс: убрать бизнес-очистку из старта приложения. Отдельный dry-run с отчётом неоднозначных связей, recoverable archive, явное решение по каждому orphan. Миграции структур не должны самовольно удалять кадровые сущности.

Приёмка: новый/повторный старт не меняет численность, зарплатную/проектную историю; сотрудник без email остаётся с понятным состоянием «нужна привязка».

## F06 — P1: существующие E2E не подтверждают текущий продукт

`playwright/shift-management.spec.ts:3-9` и `cypress/e2e/auth-flows.cy.ts:10-13` ищут username/password формы, которых нет на текущей странице Clerk. Часть shift tests допускает «Start Shift» после неуспешного start, условно пропускает ветки и использует общие данные. Поэтому наличие тестов не доказывает срабатывание операций.

Фикс: отдельная тестовая БД и Clerk test identities для admin, employee, client A/B (read/write); стабильные fixtures; строгие проверки изменившегося состояния API/БД и после reload. Тест не должен считаться успешным из-за отсутствия кнопки или появления исходного состояния. Удалить/переписать legacy fixtures. Репорт браузерного smoke составлять по достижимым маршрутам из трёх Layout.

Приёмка: полные сценарии расчёта, absent→approve→calendar, start→break→end, feedback→response, invoice→paid и documents с отрицательными проверками прав. Desktop и narrow mobile. Наличие 500/offline должно давать error/retry, не ноль или пустой список.

## F07 — P2: legacy dashboard API возвращает 500

`server/src/routes/admin.ts:194-214`: `activeTeamMembers` уже деструктурирован как первая строка, но ниже используется `activeTeamMembers[0].count`. HTTP `/admin/dashboard` →500 и `Cannot read properties of undefined (reading 'count')`. Текущий AdminDashboard использует новый `/dashboard/summary`, который ответил 200; поэтому это дефект оставленного API, не доказательство падения видимой текущей Home.

Фикс: убрать старый endpoint и клиентов или вернуть корректный контракт; приёмка — нет 500 на поддерживаемом маршруте, UI использует один dashboard DTO.
