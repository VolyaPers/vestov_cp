# Постоянное хранение файлов на Render

`render.yaml` подготовлен для одной API-инстанции с платным compute plan `0.5c-512mb`, диском `vestov-uploads` размером 5 ГБ в `/var/data` и `UPLOADS_DIR=/var/data/uploads`. Это конфигурация для проверки перед применением: сервис Render не изменялся, ресурсы не приобретались, deployment не запускался.

Render сохраняет между рестартами и deploy только файлы внутри подключённого persistent disk; такой диск требует платного сервиса. Использованы документированные поля Blueprint `runtime`, `plan`, `disk.mountPath` и `disk.sizeGB`. При применении этой конфигурации появятся расходы на compute и storage; выбран минимальный платный compute plan и небольшой диск, размер которого можно увеличить. [Render: disks](https://render.com/docs/disks), [Blueprint specification](https://render.com/docs/blueprint-spec).

Все существующие upload writers используют один `uploadsDirectory`: документы в `documents/`, контакты в `contacts/`, логотипы в `logos/`, reimbursement evidence в корне. URL и записи в БД не меняются при переносе файлов. Приватные документы по-прежнему выдаются через авторизованные маршруты.

При `NODE_ENV=production` модуль хранения отказывает в запуске, если `UPLOADS_DIR` пустой, относительный либо указывает на корень файловой системы. Проверка исключает случайный локальный fallback, но сама по себе не доказывает наличие persistent mount: это необходимо проверить в Render. В development остаётся `<working directory>/uploads`.

## Перенос существующего сервиса

1. До любого рестарта или применения Blueprint подтвердить текущую папку файлов работающего сервиса и сохранить полную резервную копию этой папки вместе со снимком БД. При текущем `cd server` стартовом скрипте локальный fallback обычно находится в `server/uploads`; фактический путь нужно проверить. Пропавшие файлы на ephemeral storage новая конфигурация восстановить не сможет.
2. Проверить предлагаемые изменения и расходы, затем отдельно применить Blueprint или вручную настроить тот же paid plan, disk mount и переменную. Исходный сервис пока не менять без разрешения на deployment.
3. Во время согласованного окна обслуживания восстановить содержимое прежней папки uploads в `/var/data/uploads`, сохранив подкаталоги и имена. Подключённый диск доступен запущенному сервису, а не build/pre-deploy процессу; перенос не добавлен в build command. Дать runtime-пользователю право чтения и записи. [Render: disk availability](https://render.com/docs/disks).
4. До возобновления работы пользователей проверить количество файлов, размеры и контрольные суммы, а затем preview/download существующих документов и evidence через их API URL. Не менять URL в БД и не удалять резервную копию после одного успешного старта.

## Приёмка после отдельного deployment

- Загрузить тестовый документ, изображение контакта, логотип и evidence; скачать их через разрешённые маршруты и сохранить SHA-256 исходных байтов.
- Перезапустить сервис и выполнить ещё один deploy без изменения диска. Скачать те же файлы и сравнить байты/хеши.
- Повторить отрицательную проверку: аноним и пользователь другой компании не получают приватный документ или evidence по прямому URL.
- Убедиться, что mount находится в `/var/data`, `UPLOADS_DIR` — под ним, а свободное место и резервные копии диска контролируются. Один диск связан с одной инстанцией; горизонтальное масштабирование потребует отдельного решения для общего хранилища. [Render: disk limitations](https://render.com/docs/disks).

В этой задаче проверены локальные guards и исходная конфигурация. Сохранность файлов реального Render-сервиса после restart/deploy ещё не проверена.
